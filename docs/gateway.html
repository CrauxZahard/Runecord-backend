Reference

Gateway.

Runecord pushes live changes over WebSockets. The native gateway is compact and typed; /gateway/v1 implements the Discord handshake if you want existing tooling to connect.

Two gateways, one event bus

Both endpoints share the same broadcast stream. The native gateway uses { op, d }; the compatibility gateway wraps the same data in Discord dispatches with sequence numbers and resume.

Endpoints

EndpointProtocolAuth
ws://127.0.0.1:47800/gatewayNative { op, d }Authorization: Bot … or Bearer …
ws://127.0.0.1:47800/gateway/v1Discord-style opcodesIDENTIFY token

Native gateway

Connect with a bot or session token in the Authorization header. The first frame is ready with the bootstrap payload, then events arrive as { "op": "message_create", "d": { … } }.

GET ws://127.0.0.1:47800/gateway
Authorization: Bot rcbot.5d41402abc4b…

Client commands

Send JSON frames to narrow the subscription or keep the socket alive. Unknown operations are ignored.

FrameEffect
{"op":"subscribe","d":{"channel_id":12}}Limit visible events to one channel
{"op":"typing","d":{"channel_id":12}}Broadcast a typing indicator
{"op":"heartbeat"}No-op keepalive

Native client example

Node's ws package lets you set the authorization header. Browser WebSockets cannot; use the compatibility gateway from a browser.

js 
import WebSocket from "ws";

const ws = new WebSocket("ws://127.0.0.1:47800/gateway", {
  headers: { Authorization: `Bot ${process.env.BOT_TOKEN}` },
});

ws.on("message", (raw) => {
  const event = JSON.parse(raw);

  if (event.op === "ready") {
    ws.send(JSON.stringify({ op: "subscribe", d: { channel_id: 12 } }));
  }

  if (event.op === "message_create") {
    console.log(event.d.author.username, event.d.content);
  }
});

Discord-compatible gateway

/gateway/v1 opens with HELLO, accepts IDENTIFY or RESUME, and emits Discord-shaped DISPATCH frames with an incrementing sequence number.

OpDirectionPayload
10 HELLOServer → client{ heartbeat_interval: 41250 }
2 IDENTIFYClient → server{ token: "Bot rcbot.…", intents }
1 HEARTBEATClient → serverSequence number or null; replies with 11
11 HEARTBEAT_ACKServer → clientnull
6 RESUMEClient → server{ token, session_id, seq }, then a replay
0 DISPATCHServer → client{ t, s, d }
9 INVALID_SESSIONServer → clientfalse

Intents

Intents are a bitfield. Omit intents or send 0 to receive everything. MESSAGE_CONTENT gates content in guild messages; direct messages keep their content.

IntentBitValueGates
GUILDS01Guild, channel, role and member events
GUILD_MEMBERS12Member updates and member pages
GUILD_PRESENCES8256Presence updates
GUILD_MESSAGES9512Guild message, typing and reaction events
DIRECT_MESSAGES124096DM message and typing events
MESSAGE_CONTENT1532768Message content in guild channels

Heartbeats and resume

Send op 1 every 41.25 seconds. The server replies with op 11. Sessions live in memory for five minutes and keep a replay buffer of 1,024 events, so a reconnect can replay what was missed.

setInterval(() => socket.send(JSON.stringify({ op: 1, d: null })), 41250);

Browser example

js 
const socket = new WebSocket("ws://127.0.0.1:47800/gateway/v1");

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({
    op: 2,
    d: {
      token: "Bot rcbot.…", // keep this server-side
      intents: 37379,
    },
  }));
});

socket.addEventListener("message", (event) => {
  const payload = JSON.parse(event.data);
  if (payload.t === "MESSAGE_CREATE") {
    console.log(payload.d.content);
  }
});
Do not expose bot tokens in a browser

The example shows the handshake shape. A browser bundle is public; proxy the socket through your own server and inject the token there.

Voice signalling

Voice uses a separate WebSocket at /voice with the same authorization header. Update presence with POST /api/voice or send a voice payload through the native gateway. The client handles media transport; the server relays signalling and participant state.
