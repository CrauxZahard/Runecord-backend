Bots & applications.

A bot is a user with a token. An application wraps a bot with install links, scopes and commands. Between the two you can build slash commands, automations and webhook integrations.

Bot accounts

Human sessions create and manage bots. Each bot gets a long-lived token, its own user ID and normal guild membership.

MethodPathAuthPurpose
POST/api/botsSessionCreate a bot and return its token once
GET/api/botsSessionList bots you own
DELETE/api/bots/{id}SessionRevoke the token and remove the bot
bash 
curl -s -X POST http://127.0.0.1:47800/api/bots \
  -H "Authorization: Bearer $SESSION" \
  -H "Content-Type: application/json" \
  -d '{"name":"Runebot","guild_id":1}'

Adding guild_id requires MANAGE_GUILD and immediately adds the bot as a member. Without it, the bot exists but belongs to no server. The token format is rcbot. plus 64 hex characters.

Bots obey permissions

A bot needs VIEW_CHANNEL to see a channel and SEND_MESSAGES to post. Give it a role instead of relying on the everyone role when you need finer control.

Applications

Applications add a product layer on top of a bot: a name, description, icon color, scopes and install links. Creating an application also creates its backing bot and returns a bot token.

MethodPathPurpose
GET / POST/api/applicationsList or create applications
DELETE/api/applications/{id}Delete an application
POST/api/applications/{id}/install-linkCreate a shareable install code
POST/api/applications/install/{code}Install into a guild with scopes and permissions
POST/api/applications/{id}/tokenIssue or rotate the app bot token
GET / POST/api/applications/{id}/commandsList or register commands
DELETE/api/applications/{id}/commands/{command}Delete a command
json
// POST /api/applications
{
  "name": "Runebot Tools",
  "description": "Utilities for Rune Lounge",
  "color": 35071
}

Installing uses a code from the install link and requires MANAGE_GUILD in the target guild. Allowed scopes are bot and applications.commands; requested permissions cannot exceed the installer's own permissions unless they are an administrator.

Application commands

Command names use lowercase letters, digits, hyphens and underscores. The application must carry the applications.commands scope. The options field is free-form JSON that the client renders and sends back in the interaction payload.

json
// POST /api/applications/3/commands
{
  "name": "ping",
  "description": "Check the bot's latency",
  "options": []
}

The client lists installed commands with GET /api/guilds/{id}/commands and invokes one with POST /api/interactions. The server creates a pending interaction and emits interaction_create to the application's bot over the gateway.

Interactions

The interaction payload includes a one-time token. Respond within the request lifetime with type 4 (channel message with source) or acknowledge with type 5 (deferred).

json
// POST /api/interactions/{id}/{token}/callback
{
  "type": 4,
  "data": { "content": "pong" }
}
Two response types are supported

4 sends a channel message immediately. 5 defers the response and returns { ok: true, deferred: true }. Other types are rejected with 400.

Webhooks

Webhooks post into one channel with a tokenized URL. They do not need a session or a gateway connection, which makes them a good fit for CI, alerts and cross-service notifications.

MethodPathAuthPurpose
GET / POST/api/channels/{id}/webhooksSessionList or create channel webhooks
DELETE/api/webhooks/{id}SessionDelete a webhook
POST/api/webhooks/{id}/{token}TokenExecute the webhook

Creating a webhook requires MANAGE_WEBHOOKS. The response includes the token, prefixed rcwh., exactly once.

bash
curl -s -X POST http://127.0.0.1:47800/api/webhooks/7/rcwh.9a1f… \
  -H "Content-Type: application/json" \
  -d '{"content":"Deploy finished","username":"CI"}'

A complete echo bot

This Node script connects to the native gateway and replies to !ping. It uses the bot token for both the socket and the send call.

js 
import WebSocket from "ws";

const BASE = "http://127.0.0.1:47800";
const TOKEN = process.env.BOT_TOKEN;

const ws = new WebSocket("ws://127.0.0.1:47800/gateway", {
  headers: { Authorization: `Bot ${TOKEN}` },
});

ws.on("message", async (raw) => {
  const event = JSON.parse(raw);
  if (event.op !== "message_create") return;
  if (event.d.author.is_bot) return;
  if (!event.d.content.startsWith("!ping")) return;

  await fetch(`${BASE}/api/channels/${event.d.channel_id}/messages`, {
    method: "POST",
    headers: {
      Authorization: `Bot ${TOKEN}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ content: "pong" }),
  });
});

Practical notes

  • Store bot and webhook tokens in a secret manager, never in a browser bundle.
  • Subscribe to the narrowest channel or intents you need.
  • Handle rate limits rather than retrying tight loops; honour Retry-After.
  • Use nonce when retrying a send so a duplicate is easier to detect.
  • Delete unused bots and webhooks; tokens are revoked immediately.
