Concepts

Authentication & tokens.

Two schemes, one rule: every request is authenticated as a user. People use short-lived sessions, bots use long-lived tokens, and permissions are enforced the same way for both.

Two auth schemes

SchemeHeaderUsed by
BearerAuthorization: Bearer <token>Human sessions from register or login
BotAuthorization: Bot rcbot.…Bot users and applications

The server parses both schemes in auth_user. Human-only endpoints such as bot creation, application management and friend requests use auth_human and reject bot tokens.

# human session
Authorization: Bearer 4f9c2a8e…

# bot
Authorization: Bot rcbot.5d41402abc4b…

Session tokens

POST /api/register and POST /api/login return a 64-character hex token alongside the user object. Store it in memory or an OS keychain, and send it on every request.

bash 
curl -s -X POST http://127.0.0.1:47800/api/register \
  -H "Content-Type: application/json" \
  -d '{"username":"maya","password":"correct horse"}'

Sessions persist until they are revoked. POST /api/logout deletes the current token; deleting the user or rotating credentials invalidates the rest. Tokens are stored as SHA-256 hashes, so a database read does not expose usable credentials.

Bot tokens

Bot tokens start with rcbot. followed by 64 hex characters. They are created by POST /api/bots, returned once, and then only their hash is retained.

# create as a human session
curl -X POST http://127.0.0.1:47800/api/bots \
  -H "Authorization: Bearer $SESSION" \
  -d '{"name":"Runebot","guild_id":1}'

# response
{ "bot": { "id": 42, "is_bot": true }, "token": "rcbot.5d41…" }

A bot is a normal users row with is_bot = 1. It can be a guild member, hold roles, author messages and appear in mentions. The token must include the bot scope, which is granted on creation.

Never ship a bot token to a client

Anyone with the token can act as the bot. Keep it on the server, rotate it if it leaks, and revoke it with DELETE /api/bots/{id}.

Permissions

Permissions are a 64-bit bitfield. A guild member's effective permissions are the base role permissions combined with channel overwrites. ADMINISTRATOR bypasses channel checks.

PermissionBitControls
VIEW_CHANNEL10See a channel at all
SEND_MESSAGES11Post in a text channel
MANAGE_MESSAGES13Delete and pin other people's messages
READ_MESSAGE_HISTORY16Read messages sent before joining
CONNECT20Join a voice channel
SPEAK21Transmit audio
MANAGE_ROLES28Create, edit and assign roles
MANAGE_GUILD5Edit server settings and add bots
ADMINISTRATOR3Bypass permission checks

Check GET /api/guilds/{id}/permissions for the caller's base permissions and GET /api/channels/{id}/permissions for overwrites. The client computes the same values locally from the guild payload.

Errors

Native endpoints return a JSON object with a single error string. The Discord-compatible surface returns { code, message } with Discord error codes.

# native
{ "error": "you don't have permission to do that" }

# /api/v1
{ "code": 50001, "message": "Missing Access" }
StatusMeaning
400Invalid body, name or parameter
401Missing, invalid or revoked token
403Authenticated but missing a permission
404Unknown guild, channel, message or user
429Rate limit exceeded
500Storage or server failure

Rate limits

Limits are bucketed per actor, route and major ID, with an additional global bucket of 50 requests per second. Every response carries the bucket state.

X-RateLimit-Limit: 60
X-RateLimit-Remaining: 59
X-RateLimit-Reset: 1794691200.120
X-RateLimit-Reset-After: 0.120
X-RateLimit-Bucket: "a1b2c3"

Default buckets include 5 requests per 60 seconds for login and register, 5 per 5 seconds for message sends, edits and reactions, 10 uploads per minute, 2 bot creations per minute and 60 reads per minute.

A limited request returns 429 with Retry-After and, for global limits, X-RateLimit-Global: true.

{
  "code": 0,
  "message": "You are being rate limited.",
  "retry_after": 4.746,
  "global": false
}

Token safety

  • Use HTTPS in production; bearer and bot tokens are passwords.
  • Do not log authorization headers or paste tokens into issues.
  • Keep data/key.bin out of backups you do not control.
  • Revoke rather than overwrite: POST /api/logout for sessions, DELETE /api/bots/{id} for bots.
  • Rate-limit your own retries and honour Retry-After.
